# hush-server 压测记录

工具：`cmd/hush-loadtest`（用法见 [README.md](README.md)「压测」一节）。

## 环境与方法

- 机器：Apple Silicon，18 核，128GB 内存，macOS；**客户端与服务端同机、走回环网络**，其他工程师的构建任务也在同一台机器上跑，数字只代表量级。
- 服务端：`--dev --addr 127.0.0.1:8095 --turn-port 0 --admin-addr ""`，临时数据目录，日志写到文件；`ulimit -n 65536`。
- 客户端：2000 个用户全部在线（各一条 WebSocket），每 5 人一个小圈子互为好友，每人 5 条朋友圈；另有 200 人群与 500 人群（群主是 0 号用户，因此它有约 500 个好友）。
- 单聊：N 个并发闭环发送（随机发送方 → 小圈子里的随机好友），256B，每档 15 秒；接收方**逐条 ack**（与真实客户端一致）。
- 端到端延迟 = 发送方发请求前打点 → 接收方从 WebSocket 读到这一帧。错误率 = 失败的发送 / 全部发送。丢失 = 已被服务端接受但 15 秒内没收到的信封。
- 群消息：成员全部在线，轮流以不同成员身份发送；延迟按「每一次投递」统计（一条消息 × 199 个接收方 = 199 个样本）。
- 读延迟：`/v1/me`、`/v1/friends`、`/v1/moments/feed` 各 2 个协程循环请求（间隔 2ms），外加 1 个协程请求 0 号用户的动态流；几组探针**同时**进行。
- 大群发大消息：500 人群里每 200ms 发一条，同时 4 个协程（不在群里的用户）循环 `GET /v1/me`、4 个协程循环 `GET /healthz`，量其他请求的最大停顿。

### 目标达成情况

方案 P6 的目标：2000 并发连接下单聊端到端 P95 < 200 ms、吞吐 ≥ 1000 条/秒、错误率 < 0.1%。

- **全部达成**：2000 在线、发送并发 256 时端到端 P95 14.7 ms、吞吐约 2.2 万条/秒、错误率 0%，零丢失零重复。
- 单聊吞吐提升约 5 倍（不再在约 4000 条/秒封顶），高并发下 P95 降低一个数量级。
- 读请求不再被写排队：写压下读延迟与空闲时同一量级。
- 群发大消息不再拖住全站：500 人群发 256KB 时其他请求最大停顿从 1.2 秒降到 39 ms。

### 剩余瓶颈

- 写入仍是单连接（为保证「提交顺序 = 队列序号」），吞吐上限由组提交批大小与 SQLite 写入速度决定；进一步扩展需要换掉这个顺序假设（多写者或外部消息队列）。
- 群消息高并发（8 个并发发送方）时 P95 约 93 ms，耗时分布尚未剖析，是下一步优化的首选目标。
- 数字来自客户端与服务端同机回环，真实网络与真机客户端需另测。
