# hush-server 接口补充说明

契约以 `docs/superpowers/specs/2026-09-24-hush-design.md` 第 3 节为准，接口 v2 的新增项见 `docs/superpowers/specs/2026-09-24-api-v2.md` 第 1 节（S-A…S-F）。本文件只记录**契约没写到、由服务端自行确定的细节**，客户端（hushcore）请按此对接。

## 通用

1. **空值用 `null`**：`Profile.avatar_id`、`Group.avatar_id`、`Comment.reply_to`、Olm 信封的 `group_id` / `session_id` 没有值时输出 `null`（字段始终存在）。
2. **契约未写响应体的写操作返回 `{}`**：包括 accept/reject 好友申请、`DELETE /v1/friends/{id}`、拉黑/取消拉黑、`POST /v1/messages/ack`、点赞/取消点赞、删除动态、删除评论、`DELETE /v1/groups/{id}/members/{uid}`。
   例外：群的 `PUT /v1/groups/{id}`、`POST /v1/groups/{id}/members`、`PUT /v1/groups/{id}/admins/{uid}` 返回**最新的 `Group`**。
3. **列表一律输出 JSON 数组**，空列表输出 `[]`，不会是 `null`。
4. **额外的错误码**：`internal`（500），`method_not_allowed`（405）。未知路由返回 404 `not_found`。所有错误体都是 `{"error","message"}`。
5. 错误码与 HTTP 状态的对应：`bad_request` 400、`unauthorized` 401、`forbidden` / `not_friends` / `blocked` 403、`not_found` 404、`conflict` 409、`too_large` 413、`rate_limited` 429、`internal` 500。
6. `Authorization` 头的 `Bearer` 前缀大小写不敏感。`?token=` **只在 `GET /v1/ws` 上接受**（与契约一致），其他接口带 `?token=` 视为未认证（401）。WS 上请求头与 `?token=` 同时存在时以请求头为准。
7. 另外提供 `GET /healthz` → `{"ok":true}`，无需认证。
8. 服务端**不解码** `body`、`key`、`signature` 等 base64 字段，只当作不透明字符串（带不带填充都可以），不做格式校验。
9. 所有 JSON 输出（HTTP 响应、队列、WS 帧）**不做 HTML 转义**：`<`、`>`、`&` 原样输出，不会变成 `\u003c` 之类的转义序列。

## 3.1 账号

- 邮箱先去掉首尾空白再转成小写（注册、登录、搜索都这样处理），因此 `GET /v1/users/search` 不区分大小写。
- 验证码错误、过期或已作废 → 401 `unauthorized`。同一邮箱 60 秒内重复请求 → 429 `rate_limited`。验证码输错 5 次即作废，需要重新申请。
- **按邮箱的滚动失败上限**：同一邮箱 1 小时窗口内累计输错 10 次（跨多个验证码累计，重发不清零）即锁定到窗口结束：期间 `POST /v1/auth/code` 与 `POST /v1/auth/verify`（即使验证码正确）都返回 429 `rate_limited`。登录成功后计数清零。
- **按对端 IP 限速**：`POST /v1/auth/code` 每个 IP 每分钟 10 次，`POST /v1/auth/verify` 每分钟 30 次，超出返回 429 `rate_limited`（计数在进程内存中）。`--addr` 为回环地址（`scripts/run-server.sh` 默认）时不按 IP 限速：本机的模拟器与测试机器人都来自 127.0.0.1，限速只会让它们互相挤占。
- `platform` 不强制只能是 `android`/`ios`，任意字符串都接受（最长 32），`device_name` 最长 128，两者都可以为空。
- 新用户的默认昵称取邮箱 `@` 前面的部分。昵称为 1–64 个字符，签名不超过 256 个字符。
- `PUT /v1/me/profile` 里的 `avatar_id` 必须是已上传的附件，否则返回 404。传空串 `""` 表示清除头像。
- 用户**首次**注册时 `device_generation=1`，此后每次 verify 加 1。
- 重新登录（非新用户）会清空该用户队列里的**全部**信封与**事件**，不只是加密信封，像待处理的 `friend_request`、`group_updated`、`moment_notification` 事件也会一起清掉。因此客户端登录成功后，必须通过 `GET /v1/friends/requests`、`GET /v1/friends`、`GET /v1/groups`、`GET /v1/moments/notifications` 做一次全量同步，不能依赖积压事件。
- 重新登录时，给旧连接发的 `logged_out` 帧**不带 `id`、不入队列**（旧 token 已经作废），发完后用关闭码 **4001** 断开。
- `key_changed` 与 `profile_updated` 发给「好友 ∪ 共同群成员」，比契约写的「好友」**范围更大**，这样同群的非好友也能及时更新会话和昵称。
- `POST /v1/auth/logout` 会同时断开该用户的 WS（关闭码 4001），但不清除密钥。
- 未配置 SMTP、也没有加 `--dev` 时，`POST /v1/auth/code` 返回 500 `internal`（「未配置邮件发送」）。配置了 SMTP 且开了 `--dev` 时，既发邮件也打日志。
- 服务端日志中的邮箱一律打码（如 `a***@example.com`），`--dev` 下打印的验证码本身不打码。
- `HUSH_DEV_CODE`（固定验证码）只在 `--dev` **且** `--addr` 为回环地址（`127.0.0.1` / `::1` / `localhost`）时生效，否则启动时告警并忽略。`scripts/run-server.sh` 默认监听 `127.0.0.1:8080`，可用 `HUSH_ADDR` 覆盖。

- **`Profile.email`（v2 S-B）**：可选字段，仅当查看者是本人或与该用户**互为好友**时出现，否则整个键省略（不是 `null`）。出现在：`GET /v1/me`（始终有）、`GET /v1/users/{id}`（本人或好友）、`GET /v1/friends`、好友申请的 `from` / `to`（`GET /v1/friends/requests`、`POST /v1/friends/requests` 的响应与 `friend_request` 事件，申请双方可见彼此邮箱）。**不出现**在：`GET /v1/users/search`（维持原样）、`PUT /v1/me/profile` 的响应与 `profile_updated` 事件（该事件也发给非好友的共同群成员）、朋友圈里的各种 `Profile`（作者、点赞、评论、通知的 `from`）、群信息。
- **令牌滑动过期（v2 S-C）**：令牌连续 `--token-ttl`（默认 90 天）未使用即失效，之后所有接口返回 401 `unauthorized`，WS 握手（`GET /v1/ws`）在升级前就返回 HTTP 401。每次通过鉴权都算一次使用，但 `last_used_at` 写库节流为**每小时最多一次**，因此实际的闲置上限在 `ttl - 1h` 到 `ttl` 之间。过期的令牌在下次被使用时删除。`--token-ttl 0` 表示永不过期（测试用）。v4 迁移时已有令牌的最近使用时间取迁移时刻。已建立的 WS 连接不因令牌过期而断开（连接期间每次重连都会重新鉴权）。

- **写操作限速**：会向他人推送事件的写接口按（用户, 操作类别）限速，每类每分钟 30 次，超出返回 429 `rate_limited`。类别：发好友申请；`PUT /v1/me/profile`；建群 / 改群资料 / 加人 / 移除成员（含退群）/ 设置管理员（共用一个类别）；点赞与取消点赞；评论。

## 3.2 预密钥

- `PUT /v1/keys` 对 OTK 采用**追加**语义：`key_id` 相同时覆盖。fallback 直接替换。单次最多上传 500 个 OTK。
- identity/signing key 在同一 `device_generation` 内不能改：值不同返回 409 `conflict`，值相同则可以重复上传。
- `claim` **只允许好友或共同群成员**调用，且**任一方拉黑了另一方时不允许**（与能发 Olm 消息的判定完全一致），否则 403 `forbidden`（包括 claim 自己、claim 不存在的用户）。这样陌生人或被拉黑的人无法反复 claim 耗尽他人的 OTK。
- `claim` 按（调用者, 目标）限速：**每分钟 10 次**，超出返回 429 `rate_limited`。计数在进程内存中，服务端重启后清零。
- 关系检查通过后，目标用户没上传过密钥，或 OTK 与 fallback 都没有时，`claim` 返回 404 `not_found`。
- `one_time_key` 对象的字段是 `{key_id, key, signature, fallback}`。OTK 按上传顺序先进先出地消耗。

## 3.3 消息

- `urgent` 省略时按 `true` 处理。
- `POST /v1/messages` 每条结果**始终包含** `to`、`client_id`、`id`、`server_ts` 四个字段；失败的条目 `id=""`、`server_ts=0`，同时带 `error`。成功的条目不带 `error` 字段。整个请求仍返回 200。
- 单条结果可能出现的 `error`：`bad_request`（缺字段、`type` 不是 0/1、发给自己、`to` 不是规范 UUID、`client_id` 格式不对）、`too_large`（`body` 超过 1MB 字符，或序列化后的信封超过单帧上限）、`not_found`（接收方不存在）、`blocked`、`not_friends`。
- **字段格式**：`to` 必须是 36 字符的 UUID。`client_id` 可以省略；若提供，须为 1–128 个字符，且只能包含 base64（标准与 URL 安全）/ UUID 字符：`A-Z a-z 0-9 + / = - _`。Megolm 的 `session_id` 必填，规则与 `client_id` 相同（先校验群成员身份，再校验格式）。
- 单次最多 1000 条，请求体上限 16MB。
- **Megolm 信封的 `type` 固定为 0**。
- Olm 批量发送时，全部接收方的关系（存在、拉黑、好友、共同群）用**一次集合查询**校验（v2 S-F），单条结果的错误码与优先级不变：格式错误（`bad_request`）与 `too_large` 先于关系错误。
- Megolm 扇出时会**跳过已拉黑发送者的成员**。非群成员发送返回 403 `forbidden`，群不存在返回 404 `not_found`。
- Megolm 群消息里，**所有接收方拿到的信封 `id` 都一样**，并且等于发送响应里的 `id`。
- `GET /v1/messages?limit=100` 的**响应格式**是 `{"messages":[信封...], "events":[事件 d...]}`。两个数组内部各自按入队顺序排列，不删除任何数据（仍需 ack）。`limit` 是两者合计的条数，最大 500。`events` 里每项与 WS 事件帧的 `d` 完全相同，都带 `id`。
  单页还受**累计负载 8MB** 限制：超过时提前截断（至少返回 1 条），因此返回条数少于 `limit` 不代表队列已空，客户端应 ack 后继续拉取，直到返回空数组。WS 积压推送同样按每批 8MB 分批读取（对客户端透明）。
- `POST /v1/messages/ack` 与 WS 的 `ack` 对信封 id 和事件 id 一视同仁。HTTP 单次最多 1000 个（超出 400）；WS 的 `ack` 帧超过 1000 个 id 时**分批全部确认**（不再截断）。
- ack 时会校验所用 token 仍然有效：用户已在别处重新登录（旧 token 作废）后，旧设备的 ack 不删除任何数据——HTTP 返回 401 `unauthorized`，WS 以关闭码 **4001** 断开。这样旧设备不会 ack 掉本该投递给新设备的信封。同理，`PUT /v1/keys` 的设备代按 token 在事务内确定，token 已作废返回 401。
- **接收方队列配额**：每个用户的队列最多 **10000 条 / 200MB**（按负载的 UTF-8 **字节**计，含事件）。配额检查与入队在同一个数据库事务内完成，多个发送方并发发送也不会超限。超出时**拒收新信封，不丢弃已有数据**：Olm 条目返回 `too_large`；Megolm 群消息跳过该成员（其他成员照常投递，发送方仍收到 200，服务端记日志）。**服务端事件不受此限制**（事件由服务端生成且体积小，丢弃会导致群/好友状态不一致）。接收方 ack 之后即可继续接收。
- **队列保留期 30 天**：入队超过 30 天仍未 ack 的信封与事件会被后台任务（启动时一次、之后每小时一次）删除。

## 3.4 WebSocket

- 投递顺序：连接后先按入队顺序推送全部积压（信封与事件混排），再发 `{"t":"queue_empty"}`，之后实时推送。同一条数据在同一连接上不会推两次，但未 ack 的数据在**重连后会重发**（至少一次投递，客户端按 id 去重）。
- 同一用户建立新连接时，旧连接以关闭码 **4000**（replaced）断开。
- 建立连接时 token 已被重新登录或退出登录作废（包括鉴权通过之后、连接登记之前才作废的情况），连接以关闭码 **4001** 断开，不会成为当前连接，也不会以 4000 挤掉新设备的连接。
- 服务端 90 秒内收不到任何客户端帧就断开连接（客户端每 25 秒发一次 ping）。客户端发给服务端的单帧上限 1MB。
- **服务端推送的单帧上限为 `1MB + 64KB`（1114112 字节）**，入队前就按此校验（超出的 Olm 条目返回 `too_large`，Megolm 整个请求 413 `too_large`）。万一队列里已有超限项（例如旧数据），推送时直接从队列删除并记日志，不会卡住后续数据。客户端的读帧上限应与此一致。
- 事件 `d` 的形态是**扁平的**：`{"id","type", ...字段}`，例如 `{"id":"…","type":"friend_accepted","user_id":"…"}`。
- 事件的发送对象：
  - `friend_request{request}` → 被申请人。
  - `friend_accepted{user_id}` → 原申请人（`user_id`=接受方）；互相申请时自动成为好友，此事件同样发给对方。
  - `friend_removed{user_id}` → 被删除的一方。
  - `group_updated{group}` → 变更后的全体成员。
  - `group_removed{group_id}` → 被移除或退群的人。
  - `moment_notification{notification}` → 通知接收人。
- **事件合并**：以下事件在入队时会替换接收方队列里**同一主体**尚未 ack 的旧事件（新事件带新的 `id`，排在队尾），防止反复操作灌满他人队列：`friend_request`（同一条申请）、`group_updated`（同一个群）、`profile_updated`（同一个用户）、`key_changed`（同一个用户）、点赞类 `moment_notification`（同一条动态的同一个点赞者）。旧事件之后如果已经有信封，就不合并（保证事件与消息的相对顺序，例如新成员的消息不会先于把他加进群的 `group_updated`）。这些事件都携带完整的最新状态，所以只处理最新一条即可；客户端 ack 已被替换的旧 id 是无害的空操作。
- **事件与业务变更在同一事务内写入队列（outbox，v2 S-D）**：两者一起提交或一起回滚——请求中途失败或客户端断开导致回滚时，业务变更与事件都不生效；一旦提交，事件就已持久化，进程在提交之后、推送之前崩溃也不会丢，客户端重连后作为积压收到。在线推送（唤醒 WS 连接）在事务提交之后才触发，因此客户端收到事件时，对应的状态一定已经可以通过 HTTP 查到。事件合并、队列配额与写接口限速的语义不变。
- 离线推送（`Pusher`）只对**离线且 urgent 的信封**触发，事件不触发。

## 3.5 好友与拉黑

- 对方已经给我发过待处理申请时，我再 `POST /v1/friends/requests` 会**直接成为好友**，返回对方那条申请（`status:"accepted"`，`from`=对方）。
- 我已经给对方发过待处理申请时再发一次，会复用原申请（更新留言与时间），并重新推送 `friend_request`。同一 (申请人, 被申请人) 任何时候最多只有一条待处理申请，客户端并发重试也不会产生重复申请；双方同时互相申请时必然直接成为好友。重复接受同一条申请只有第一次成功（其余 409），`friend_accepted` 只发一次。
- 已经是好友 → 409 `conflict`。任一方拉黑了另一方 → 403 `blocked`。发给自己 → 400。
- `status` 取值为 `pending | accepted | rejected`。拒绝时不通知申请人。
- 只有被申请人能 accept/reject，其他人调用返回 404。申请已处理过则返回 409。
- `DELETE /v1/friends/{id}` 是幂等的，对方原本就不是好友也返回 `{}`。
- **拉黑不会自动删除好友关系**，只是阻断双方的 Olm 消息与好友申请。
- 契约写的是「未互相拉黑」，实现时按「任一方拉黑另一方」判定，所以**拉黑方自己也发不出去**。

## 3.6 群组

- 群名 1–64 个字符，公告最多 2000 个字符，每群最多 500 人（加人时在同一事务内核对，并发加人也不会超过；名单里已是成员的人不占名额，超出返回 400）。`member_ids` 会去重，并自动排除创建者本人。
- 建群时，全体成员（含创建者）都会收到 `group_updated`。
- 群不存在 → 404。非成员查看或操作 → 403 `forbidden`。
- **踢人权限**：群主可以踢任何人；管理员只能踢普通成员。
- **群主退群**：群主身份转给最早加入的管理员，没有管理员就转给最早加入的成员。最后一人退出时群被删除，这种情况下只给退出者发 `group_removed`。
- 群主自己的角色不能用 `admins` 接口修改（400）。
- `avatar_id` 传空串 `""` 表示清除；非空时必须是已上传的附件，否则 404 `not_found`（与个人头像一致）。

## 3.7 附件

- 上传 0 字节 → 400。超过 100MB → 413 `too_large`。
- **每用户 24 小时（滚动窗口）上传总量上限 2GB**，超出返回 429 `rate_limited`。进行中的上传会按 `Content-Length` 预占额度，并发上传也不会突破上限（未声明长度的分块上传在读完后按实际大小核对）。
- 下载需要认证，任何已登录用户凭 id 都能下载（id 是随机 UUID）。下载支持 HTTP `Range`。服务端日志中的附件 id 只保留前 8 个字符。
- **90 天未被访问（下载）的附件会被删除**（元数据与文件），被用户头像、群头像或朋友圈图片引用的附件除外（朋友圈引用按 `moment_media` 关联表判断，v5 迁移时从已有动态回填；删除动态后其图片不再算被引用）。访问时间在下载时更新（距上次记录超过 1 天才写库）。删除后下载返回 404。清理时先移走文件、再按同样的引用条件删除元数据：文件无法删除时元数据保留（下次再试），挑出候选之后才被引用的附件不会被删。进程崩溃残留的上传临时文件超过 1 天后删除。
- 上传与下载路由的读写超时放宽到 10 分钟；其他接口的全局超时为读 60 秒、写 60 秒、请求头 15 秒、空闲连接 120 秒；WebSocket 不受全局读写超时限制。

## 3.8 朋友圈

- `visibility` 省略时等于 `all`。`mode=all` 时忽略 `user_ids`。include/exclude 名单只对作者的好友生效，名单里的非好友本来就看不到。
- 文字与图片不能同时为空。文字最多 5000 个字符，图片最多 9 张，图片的 `attachment_id` 必须是已上传的附件。评论为 1–1000 个字符。
- `GET /v1/moments/user/{uid}`：**非好友返回 `[]`**，不报错。`uid` 不存在返回 404。
- **`GET /v1/moments/{id}` → `Moment`（v2 S-A）**：可见性与动态流相同（作者本人，或作者的好友且在可见范围内），点赞/评论只保留查看者本人或其好友产生的条目，`visibility` 只对作者返回——与该动态在动态流里的样子完全一致。不存在、已删除、对查看者不可见都返回 404 `not_found`（不泄露存在性）。
- 分页：`before` 是毫秒时间戳（不含该时刻），缺省表示从最新开始。`limit` 默认 20，最大 100。通知接口 `limit` 默认 50，最大 200。
- **可选参数 `before_id`**（动态流、某人动态、通知三个接口都支持）：与 `before` 组成 `(created_at, id)` 复合游标，返回「`created_at < before`，或 `created_at = before` 且排在 `before_id` 之后」的条目，与排序（时间倒序、同一时刻按写入顺序倒序）一致。翻页时传上一页最后一条的 `created_at` 与 `id`，同一毫秒的多条跨页时不会漏。不传或 id 不存在时保持原来的 `created_at < before` 语义。`before_id` 最长 64 字符。
- 对查看者**不可见**的动态，点赞、评论、删除都返回 404。
- 点赞是幂等的，重复点赞不会重复通知。取消点赞时会一并删除对应的点赞通知。
- `reply_to_user_id` 必须是存在的用户。
- **回复通知**只在满足以下条件时发送：被回复者能看到这条动态，且与评论者互为好友（与微信「只能看到共同好友」的规则一致）。
- 通知对象**不含 `comment_id`**。`text` 只在 `kind=comment` 时出现，`like` 时省略这个字段。
- 删除评论时一并删除其通知。删除动态时，其点赞、评论、通知全部删除。
- 删除评论只能由评论作者或动态作者操作，其他人 → 403。删除动态只能由作者操作，其他人 → 403。

## 3.9 通话

- `urls` 里的主机是**客户端访问 HTTP 时用的主机名**（取自请求的 Host，例如 Android 模拟器上是 `10.0.2.2`），端口为 `--turn-port`，这样保证客户端能连上。`--public-ip` 只作为 TURN 分配的中继地址。
- `username` 里的 expiry 与 `ttl` 都以**秒**为单位（TURN REST 惯例），这是契约「时间戳均为毫秒」的例外。默认 `ttl=86400`。
- TURN 端口被占用或启动失败时，只记一条警告日志，HTTP 服务照常运行。`--turn-port 0` 表示不启动 TURN。这两种情况下 `GET /v1/calls/turn` 返回**空的 `urls` 数组**（`username`/`credential`/`ttl` 照常返回），客户端应只使用直连候选。
- **中继目标过滤**（CreatePermission / ChannelBind）：始终拒绝未指定地址、组播、广播与 `0.0.0.0/8`；**生产模式**另外拒绝回环、私有（`10/8`、`172.16/12`、`192.168/16`、`fc00::/7`）、链路本地（`169.254/16`、`fe80::/10`）与 `100.64/10`，防止 TURN 被当作跳板访问服务端内网或本机服务。**`--dev` 下允许这些地址**，因为本地联调时双方都在本机或模拟器上（ICE 候选多为回环 / 私有地址）。被拒绝时服务端记一条日志。
